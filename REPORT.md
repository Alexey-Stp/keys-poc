- Environment isolation, tenant overrides, binary keys and every negative check behave as designed.

## Discrepancies and what had to change

1. **`toJSON(secrets)` blocks the whole run.**
   - With that one step, the run ends immediately as `action_required` with no jobs, both on push and on dispatch.
   - I ruled out the other causes: no pending deployments, no environment protection rules, and the repo allows all actions.
   - Removing only that step made the same workflow run (check 4).
   - Consequence: don't pass all secrets in one block. That also rules out picking tenant secrets dynamically in `production-deployment-all`.
2. **Trailing newline is lost on raw-text secrets.**
   - Secrets were uploaded byte-exact with `gh secret set NAME < file`.
   - On the runner, each text key is missing its final `\n`, or `\r\n` for the CRLF `.p8`.
   - I didn't isolate whether `gh` or GitHub strips it.
   - Base64 values (`KEY_LEGACY_P12`, `TENANT_KEYS`) are byte-exact.
   - Some OpenSSH and PGP readers reject a key without its final newline. I haven't checked whether SSH.NET and the PGP library in the app do.
   - **Proposed fix (not applied, to keep the test as specified):** store every key as base64, or ship the shared keys as one base64 zip like `TENANT_KEYS`.
3. **Tenant artifact contents.**
   - Uploading the full `servers` snapshot per tenant breaks verify's layering: initech's snapshot still holds carecorp's state before its custom keys and overwrites them.
   - `servers-after-<tenant>` now contains only that tenant's folder.
   - This is plumbing of the mock (real runners write to disk directly), not part of the scheme.
4. **Tenant SFTP key file name.**
   - The spec says each tenant gets "its own `sftp_rsa`". I packed it as `SSC_SFTPPrivateKey.openSSH`, so it replaces the shared key instead of sitting next to it.
   - The override works.
5. **Environments get created implicitly.** `environment: globex` created an empty environment; I deleted it afterwards. A typo in a tenant name does the same, and only the empty-`TENANT_KEYS` check catches it.
6. **The earlier PoC's `carecorp1` environment came back.**
   - It reappeared at 14:25 after being deleted at about 14:17, though no workflow refers to it. It still had old deployment records.
   - Cause unknown; I deleted it again.
7. **`deploy-all` status glitch.** In run 39795147250 the API still reports `deploy-all` as `in_progress`. Its log shows the artifact uploaded, and the three jobs that depend on it ran. This is a GitHub-side status glitch.
8. **`verify-keys.ps1` CR check.** My first version failed any file containing CR. openssl on Windows writes `.p8` and `.pem` with CRLF, so the originals contain CR. Line endings are now informational; the hash already catches any change.
9. **Leak commit still reachable.** After the PR was closed and its branch deleted, `refs/pull/1/head` still points to the commit with the test key. A real leak through a PR means rotating the key; deleting the branch doesn't remove it.
10. **Minor.**
    - `actions/upload-artifact@v4` and `download-artifact@v4` log a Node.js 20 deprecation warning.
    - In Git Bash, MSYS rewrote `openssl -subj "/CN=..."` as a path, so `generate-test-keys.sh` sets `MSYS2_ARG_CONV_EXCL`.

## What carries over to the real repository

**As-is:**
- **Writing files:**
  - Text with `WriteAllText` and UTF-8 without a BOM, binary with `WriteAllBytes`; never `Set-Content` or `Out-File`. Check 7 shows why.
  - `write-tenant-keys.ps1`: a zip in base64 with plain file names only, extracted over the shared keys. It fails clearly when `TENANT_KEYS` is empty.
- **Uploading:**
  - `pack-tenant-keys.ps1` for the support team.
  - Upload from a file or with `--body`, and check the size first. Piping from Windows PowerShell 5.1 corrupts the value (found in the earlier PoC).
- **Isolation:** environment secrets are confirmed to stay out of jobs that don't name the environment (check 5).
- **Checks:**
  - A hash manifest (`verify-keys.ps1`) as a post-deploy check.
  - The gitleaks PR check.

**Needs changes:**
- **Shared keys:** store them as base64 (discrepancy 2).
- **Secret access:** no `toJSON(secrets)` (discrepancy 1). Every secret must be referenced by name.
- **Order in `production-deployment-all.yml`.** Today one job per runner deploys every tenant and starts each app pool. A later `deploy-tenant-keys` job with `environment:` leaves a gap where a tenant runs without its own keys. Also, `robocopy /mir` purges `XML\Keys` on the next deploy unless it is preserved. Two options:
  - run the tenant-keys job on the tenant's `GH_RUNNER` before the app pool starts, or
  - add `XML\Keys` to `$PreservedTenantPaths` and accept that the gap exists only on a tenant's first deploy.
- **Tenant list:**
  - `TENANTS_WITH_CUSTOM_KEYS` must hold the exact environment names (`prod:carecorp1`).
  - It's a manual list, so it can drift from the environments that actually have `TENANT_KEYS`. A tenant left off it silently gets no tenant keys.
  - The real `list_environments` job already uses a GitHub App token and could build this list from environment secret names instead.
- **Artifacts:** passing server state between jobs as artifacts is mock-only. On real runners the files are written in place, and keys must never be uploaded as artifacts.
