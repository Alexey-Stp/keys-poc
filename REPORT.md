## Why deploy-to-all needs separate tenant-key jobs

- **Environment secrets reach only jobs that name that environment.** GitHub docs, [Deployments and environments: Environment secrets](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#environment-secrets): "Secrets stored in an environment are only available to workflow jobs that reference the environment."
- **A job names one environment.** [`jobs.<job_id>.environment`](https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions#jobsjob_idenvironment): "Use `jobs.<job_id>.environment` to define the environment that the job references." The value is a single name, or an object with one `name`.
- **Confirmed here.** The `no-environment` negative check read `TENANT_KEYS` with length 0.

So the two workflows work differently:
- **`deploy-to-tenant`** is one job with `environment: <tenant>`. It sees the repository secrets (shared keys) and that tenant's `TENANT_KEYS`.
- **`deploy-to-all`** runs one job for all tenants. It has no environment, so it sees only repository secrets. It therefore needs one extra job per tenant with its own keys (`deploy-tenant-keys`, a matrix over `TENANTS_WITH_CUSTOM_KEYS`, each with `environment: <tenant>`), run before it.

## What changed since the first round

1. **Every secret is base64** (decision 1).
   - `set-secrets.sh` base64-encodes all five shared keys before upload.
   - `write-shared-keys.ps1` has one code path: `FromBase64String` → `WriteAllBytes`. There's no text/binary split and no `WriteAllText`.
   - `-Broken` writes the decoded bytes as a string with `Set-Content`.
   - This fixed the trailing-newline loss: 14 mismatches in round 1, 0 now.
2. **`toJSON(secrets)` removed** (decision 2). It caused `action_required` with no jobs started ([39794705946](https://github.com/Alexey-Stp/keys-poc/actions/runs/39794705946), [39794909046](https://github.com/Alexey-Stp/keys-poc/actions/runs/39794909046)) and was removed without further investigation.
3. **Job order reversed, keys moved out of the app folder** (decision 3).
   - The order is `deploy-tenant-keys` → `deploy-all` → `verify`.
   - Keys live in `config\<tenant>\Keys\` (CONFIG_DIR): `shared\` and `tenant\` are merged, and both subfolders are then removed.
   - The app folder holds no keys.
   - The pool starts only after the merge.
   - The per-tenant sequence is in `scripts/deploy-tenant.ps1`. The merge is in `scripts/merge-keys.ps1`, which sets each merged file's time to the merge time, so the pool-order check means something; a plain copy would keep the old file times.
4. **`deploy-to-tenant.yml`** (decision 4).
   - One job with `environment: <tenant>`.
   - It calls the same scripts. `write-tenant-keys.ps1 -Optional` skips a tenant without `TENANT_KEYS` instead of failing.
5. **`verify-keys.ps1`** additionally fails on any of these:
   - key files under `<tenant>\app\`;
   - `app-pools-started.txt` missing, or older than the newest key;
   - `shared\` or `tenant\` left in `Keys\`.

   Before the GitHub run I checked locally that each of the three catches a deliberately broken layout.
6. **Fixed along the way: an artifact plumbing bug in my workflow.**
   - The first run of the new layout ([39799630728](https://github.com/Alexey-Stp/keys-poc/actions/runs/39799630728), commit `eb74be4`) failed in `deploy-all` with 18/23.
   - Cause: the tenant-keys artifact used a wildcard path, so it contained `SB21\config\carecorp\Keys\tenant\...` instead of the files. That nested folder was copied into `Keys\tenant\`, and the merge skipped it silently.
   - Fix (`fa58c94`): upload a flat folder. `deploy-tenant.ps1` now fails if `-TenantKeysFrom` has no files directly in it, and `merge-keys.ps1` fails if `shared\` or `tenant\` contains subfolders.
   - The verify step caught the bug, which is what it's for.

## Notes and limits (not failures)

1. **The `verify` job checks pool order only to 2 seconds.**
   - `Compress-Archive` stores file times in 2-second steps, so after the artifact round trip the pool time and the newest key time both read `15:07:02.000`.
   - It can't fail falsely, but it can't distinguish a wrong order within the same 2 seconds.
   - The same script runs on the live folders inside `deploy-all` before upload, with exact times, and that check shows the real order.
   - On real servers there's no artifact round trip.
2. **Environments are created implicitly.**
   - `environment: <name>` creates an empty environment if none exists. The negative test created `globex` again (deleted), and `deploy-to-tenant acme` created `acme` (kept: a real tenant has its own environment).
   - A typo in a tenant name creates an environment the same way. In `deploy-to-all.yml` the empty-`TENANT_KEYS` check catches it.
   - In `deploy-to-tenant` it does not, because `-Optional` skips missing tenant keys. A tenant that should have its own keys but whose secret is missing would deploy with shared keys only.
   - Suggested: in `deploy-to-tenant`, use `-Optional` only when the tenant is not in `TENANTS_WITH_CUSTOM_KEYS`. Not implemented, to keep decision 4 as specified.
3. **One tenant's keys failing stops every tenant's deploy.**
   - If any `deploy-tenant-keys` job fails, `deploy-all` doesn't run for anyone (`needs`).
   - That's safe (no tenant is touched), but one bad tenant secret blocks the whole deploy.
4. **`deploy-to-tenant` uses a free-text input.** `type: environment` would only list environments that already exist (`acme` didn't), so the input is `type: string`. A tenant missing from `tenants.json` fails in `get-tenant-server.ps1`.
5. **GitHub API status glitch, seen twice.** A job stays `in_progress` in the jobs API after it finished and the jobs that depend on it completed: `deploy-all` in run 39795147250, and `globex-no-tenant-keys` in run 39801810800. It had no effect on results.
6. **Carried over from round 1.**
   - The leak commit is still reachable via `refs/pull/1/head` after the PR was closed and its branch deleted.
   - The earlier PoC's `carecorp1` environment reappeared once after deletion; it hasn't come back since.
   - `upload-artifact@v4` and `download-artifact@v4` log a Node.js 20 deprecation warning.
   - Artifacts here contain test keys (retention 1 day). That's mock-only.

## For production

**Layout on each server:**
```
CONFIG_DIR\Keys\           final keys (shared, then tenant's own on top); the only place the app reads
CONFIG_DIR\Keys\shared\    written during deploy-all from repository secrets, removed after merge
CONFIG_DIR\Keys\tenant\    written by the tenant-keys job from the environment secret, removed after merge
APP_DIR\                   robocopy /MIR target; contains no keys
```

**What this means for `ssc-web-app`:**
- **Where the app reads keys.** Today the app reads `APP_DIR\XML\Keys`, or AppConfig `KeysPath`.
  - To read `CONFIG_DIR\Keys`, set `KeysPath` to that folder in each tenant's AppConfig.xml.
  - `docs/key-management.md` currently says not to set `KeysPath` on deployed tenants, because deploys didn't update that folder. With this scheme they do, so that guidance flips.
  - `Copy-TenantKeys` stops copying into `APP_DIR\XML\Keys`.
- **robocopy is not affected.** `Deploy-TenantBuild`'s `robocopy /mir` only touches `APP_DIR`, so keys don't need to be in `$PreservedTenantPaths`. Check 4 shows a second mirror leaves them unchanged.
- **Job order in `production-deployment-all.yml`:**
  1. A tenant-keys job per entry in `TENANTS_WITH_CUSTOM_KEYS`, with `environment: <prod:tenant>` and `runs-on` set to that tenant's `GH_RUNNER`, writes `CONFIG_DIR\Keys\tenant\` directly on the server. There's no artifact in production.
  2. The existing per-runner `build_and_deploy`, with `needs:` on step 1. In `Invoke-TenantMigrateAndDeploy`, after `Deploy-TenantBuild` and the config overlay: write the shared keys into `CONFIG_DIR\Keys\shared\`, then merge, then `Start-TenantAppPool`.
  - App pools start only after the merge.
  - Requirement: `GH_RUNNER` must name one machine, so step 1 writes to the same disk that step 2 reads.
  - If step 2 fails after step 1, a stale `tenant\` folder stays until the next run, which replaces it.
- **Names in the tenant list.** `TENANTS_WITH_CUSTOM_KEYS` must hold the exact environment names (`prod:carecorp1`). The environment names come from the real `list_environments` job.
- **`production-deployment.yml` (single site)** already has `environment:`, so it matches `deploy-to-tenant`: same scripts, plus `-Optional`, or the stricter check in note 2.
- **`qa-deployment.yml`** has no `environment:` on its deploy job, so QA tenants get shared keys only unless that job gains one.
- **Every secret is base64:** there's no exception for "text" keys. Secrets must be named explicitly in `env:`; no `toJSON(secrets)`.

## What DevOps needs to do

Run `gh` from Git Bash or cmd, not by piping from Windows PowerShell, which re-encodes the value. Keep every value under 32,000 bytes; `set-secrets.sh` shows the size check.

1. **Initial secret setup**, once per repository:
   - For each shared key: `base64 -w0 <file> > key.b64`, then `gh secret set KEY_<NAME> < key.b64`. Delete `key.b64` afterwards.
   - Set the tenant list: `gh variable set TENANTS_WITH_CUSTOM_KEYS --body '["prod:carecorp1"]'` (exact environment names).
2. **Add a tenant with its own keys:**
   1. Put the tenant's files in an empty folder, using the exact file names they should have in `Keys\`. A file named like a shared key replaces the shared one for this tenant.
   2. Pack the folder: `powershell -File scripts/pack-tenant-keys.ps1 -Folder <folder> > tenant.b64`, run from Git Bash or cmd.
   3. Upload it: `gh secret set TENANT_KEYS --env <tenant> < tenant.b64`.
   4. Add the tenant to `TENANTS_WITH_CUSTOM_KEYS`.
   5. Deploy that tenant.
3. **Rotate a shared key:**
   1. Encode the new file to base64 and set the same secret name again.
   2. Run the full deploy. Each tenant gets the new key on its next deploy.
4. **Rotate a tenant key:**
   1. Repack the tenant's complete folder with the new file. `TENANT_KEYS` replaces the tenant's whole set, so include unchanged files too.
   2. Set `TENANT_KEYS` for that environment again.
   3. Deploy that tenant.
